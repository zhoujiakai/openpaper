# 一、总体脉络

设备控制里的编程，不只是写普通业务逻辑。它更像是在软件和硬件之间搭桥。

上层应用里，程序主要处理数据、界面、网络和业务规则。设备端程序则更贴近硬件：它要读传感器、控制引脚、配置寄存器、处理中断、输出 PWM、进行串口通信，还要考虑时钟、电源、存储、看门狗和实时性。

这份内容分成四条主线：

1. C 语言：学习设备端编程的基础语言能力。
2. STM32：学习如何在单片机上用 C 语言控制真实硬件。
3. C++：学习如何在保持底层性能的同时，提高控制算法、设备抽象和业务主程序的可维护性。
4. PyTorch：学习如何实现机器学习模型，完成训练、验证、保存和部署前转换。

C 语言负责把底层能力讲清楚。它包括编译流程、类型系统、指针、数组、动态内存、结构体、函数指针、位运算、宏、编译链接和嵌入式接口。

STM32 负责把这些能力落到设备上。它包括开发环境、工程结构、GPIO、OLED、外部中断、定时器、ADC、DMA、USART、I2C、SPI、RTC、电源控制、看门狗和 Flash。

C++ 负责把设备端程序组织得更稳。它通过类、RAII、模板、多态、`constexpr`、`enum class`、`std::array` 等特性，把传感器、执行器、控制算法和业务流程封装成更清晰的模块。

PyTorch 负责把机器学习算法训练出来。它通过 Tensor、Autograd、`nn.Module`、DataLoader、训练循环、GPU 加速和模型保存加载，把数据变成可用模型。训练好的模型可以用于设备控制中的视觉识别、故障检测、传感器时序预测、状态分类和策略辅助。

如果把设备看成一个系统，C 语言像是“写控制逻辑和驱动代码的工具”，STM32 像是“承载控制逻辑的硬件平台”，C++ 像是“把算法、驱动和业务组织成可长期维护工程的结构化方法”，PyTorch 像是“在设备外训练智能模型，再把模型能力接入设备控制系统的工具链”。四者合在一起，才能完成一个完整、可靠、可扩展、可智能化的嵌入式控制项目。

# 二、C 语言部分

C 语言在设备控制方向上的作用，主要有三点：

1. 写驱动：直接操作寄存器、引脚、总线和外设。
2. 写业务主程序：把多个传感器、执行器和通信模块组合起来。
3. 理解嵌入式系统：理解内存、编译、链接、指针、位操作和硬件接口。

在设备端，C 语言不是“可选语言”，而是很多微控制器开发的默认语言。原因很简单：它足够贴近硬件，运行开销低，编译后能直接控制内存和寄存器。

## 1. 编译流程：代码怎样变成设备能执行的程序

C 程序不是像脚本一样直接运行。它要经过一条完整的构建链路：

```text
.c 源文件 -> 预处理 -> 编译 -> 汇编 -> 链接 -> 可执行文件/固件
```

预处理阶段会处理 `#include`、`#define`、条件编译等内容。头文件会被展开，宏会被替换，最终得到更完整的 C 源代码。

编译阶段会把 C 代码翻译成汇编代码。这个阶段会检查语法、类型、函数声明等问题。

汇编阶段会把汇编代码变成机器码，通常生成 `.o` 目标文件。

链接阶段会把多个目标文件和库文件合在一起，解决函数和变量之间的引用关系，最终生成可执行文件。在嵌入式里，最终产物往往会被下载到单片机 Flash 中。

这一章的意义是让人知道：C 程序不是一个孤立文件。一个嵌入式工程通常由启动文件、系统文件、外设库、用户代码、头文件和链接配置共同组成。

## 2. 类型系统：提前决定数据怎么放进内存

C 语言的变量不是随便变化的标签，而是固定类型、固定大小的内存区域。

比如 `int` 通常占 4 字节，`char` 占 1 字节，`float` 占 4 字节，`double` 占 8 字节。具体大小和平台有关，所以需要用 `sizeof` 来确认。

在设备控制中，类型大小非常重要。传感器数据、寄存器字段、通信协议数据包，往往都要求明确的字节长度。如果类型用错，可能导致数据解析错误，甚至控制行为异常。

`signed` 和 `unsigned` 用来决定整数是否有符号。无符号数常用于寄存器、位标志、计数器和数据包字节，因为它们本质上是二进制位，不一定表示正负。

`const` 表示变量不应该被修改。它可以用于保护配置参数、只读表、函数输入等。

`volatile` 在嵌入式里尤其重要。它告诉编译器：这个变量的值可能被外部因素改变，不要自作聪明地优化掉读取动作。硬件寄存器、中断中修改的变量、某些共享状态，常常需要 `volatile`。

## 3. 指针：C 语言连接内存和硬件的核心

指针是 C 语言的分水岭。

指针本质上是保存地址的变量。普通变量保存值，指针保存这个值所在的内存地址。通过 `&` 可以取地址，通过 `*` 可以解引用，也就是访问地址指向的内容。

设备控制为什么离不开指针？因为硬件寄存器本质上就是某个固定地址上的一段内存。要控制外设，就要向这些地址读写特定位。寄存器操作、数组传参、字符串处理、动态内存、驱动函数接口，都离不开指针。

函数参数在 C 里默认是值传递。函数拿到的是一份拷贝。如果想让函数修改外部变量，就要把变量地址传进去。

比如驱动函数常常写成：

```c
void Sensor_Read(SensorData *data);
```

这里传入的是结构体指针，函数可以把读取结果写回调用者提供的结构体里。

指针也会带来风险。野指针、空指针、悬垂指针、越界访问都会让程序崩溃或产生难以定位的问题。嵌入式程序没有复杂操作系统保护时，这些错误更危险。

## 4. 数组和字符串：连续内存的使用方式

C 的数组是一段连续内存。数组里每个元素类型相同，元素按顺序紧挨着排列。

数组名在很多场景下会退化成指向首元素的指针。这让数组传参变得高效，但也带来一个问题：函数里通常不知道数组长度，需要额外传入长度。

设备控制中经常用数组保存：

- 传感器采样数据
- 串口接收缓冲区
- I2C/SPI 发送缓冲区
- 滤波窗口
- 波形表
- OLED 显示缓存

C 字符串本质上是以 `\0` 结尾的字符数组。字符串处理必须注意结尾标记和缓冲区长度，否则容易越界。

在串口文本通信里，字符串很常见。比如单片机向电脑发送调试信息，或者接收一条文本命令，都需要处理字符数组和结束符。

## 5. 动态内存：手动申请和释放内存

C 语言可以用 `malloc`、`calloc`、`realloc` 和 `free` 管理堆内存。

动态内存的好处是灵活。程序可以在运行时根据需要申请不同大小的内存。

但在嵌入式开发中，动态内存要谨慎使用。原因是单片机内存有限，长期运行时容易出现内存泄漏、碎片化或分配失败。

设备控制程序通常更偏好静态分配。比如提前定义好缓冲区、结构体和任务状态，让内存布局稳定可控。

理解堆和栈也很关键。

栈通常用于局部变量和函数调用，速度快，但空间有限。

堆用于动态分配，灵活但需要手动管理。

全局变量和静态变量通常放在静态存储区，生命周期贯穿整个程序。

这些知识帮助我们判断一个变量该放在哪里，避免栈溢出、内存泄漏和不可预测的运行问题。

## 6. 结构体：把多个数据组织成一个设备对象

结构体用于把多个相关字段打包在一起。

在设备控制中，结构体非常自然。一个传感器可以有状态、配置、测量值、错误码；一个电机可以有速度、方向、PWM 占空比、编码器计数；一个通信包可以有包头、长度、命令、数据和校验。

比如：

```c
typedef struct {
    float temperature;
    float humidity;
    uint8_t status;
} SensorData;
```

`typedef` 可以简化结构体类型的写法，让代码更像在描述业务对象。

结构体还有内存对齐问题。编译器为了让 CPU 更高效访问数据，可能在字段之间插入空隙。通信协议、Flash 存储和寄存器映射中，如果直接使用结构体对应二进制数据，就必须特别注意对齐和字节布局。

## 7. 函数指针：把行为当作参数传递

函数指针保存的是函数地址。它可以让程序在运行时选择调用哪个函数。

课程里提到 `qsort` 回调，这是函数指针的经典例子。排序函数本身不知道比较规则，所以把比较函数作为参数传进去。

在嵌入式中，函数指针常用于：

- 回调函数
- 状态机
- 驱动抽象层
- 通信协议命令分发
- 中断事件处理

比如串口收到一条命令后，可以根据命令号调用不同处理函数。这样代码比一长串 `if-else` 更清晰。

函数指针语法难读，但它表达的思想很重要：数据可以传递，行为也可以传递。

## 8. 位运算：嵌入式寄存器控制的基本动作

位运算是 C 语言和嵌入式之间最直接的接口。

常用位运算包括：

- `&`：按位与
- `|`：按位或
- `^`：按位异或
- `~`：按位取反
- `<<`：左移
- `>>`：右移

寄存器通常由很多位组成，每一位或几位控制一个功能。比如某一位控制时钟使能，某几位选择 GPIO 模式，某一位表示中断标志。

常见操作模式是：

```text
设置某一位：reg |= mask
清除某一位：reg &= ~mask
翻转某一位：reg ^= mask
读取某一位：reg & mask
```

这部分是 STM32 寄存器编程的基础。理解位运算后，才能理解为什么写一个寄存器值就能打开时钟、配置输出模式或清除中断标志。

## 9. 宏与预处理器：编译前的文本处理

宏是在预处理阶段完成的文本替换。它可以定义常量、封装简单表达式、控制条件编译。

宏很强，但也容易出问题。比如宏参数如果不加括号，可能因为运算优先级导致错误。因此宏的基本习惯是：参数加括号，整体也加括号。

条件编译常用于嵌入式：

```c
#ifdef DEBUG
    // 调试代码
#endif
```

它可以让同一份代码在调试版、发布版、不同芯片型号或不同硬件配置下编译出不同结果。

`#include` 的本质是把头文件内容复制进来。头文件通常放函数声明、类型定义、宏定义和外部变量声明。源文件放函数实现和变量定义。

## 10. 编译与链接：多文件工程怎样组织起来

真实嵌入式工程不会把所有代码写在一个 `.c` 文件里。它通常会拆成多个模块：

- `main.c`：主程序
- `delay.c`：延时函数
- `led.c`：LED 驱动
- `key.c`：按键驱动
- `oled.c`：显示驱动
- `usart.c`：串口驱动
- `sensor.c`：传感器驱动

这就需要理解声明和定义。

声明告诉编译器“这个函数或变量存在，长这样”。

定义真正分配空间或提供函数实现。

头文件用于共享声明，源文件用于提供定义。

多文件编译最后要靠链接器把各个模块合并起来。Make、CMake 或 IDE 工程配置，都是在帮助管理编译和链接过程。

静态库和动态库也是链接阶段的重要概念。嵌入式项目中常见的是静态链接，把所需代码一起打进最终固件。

## 11. 常见陷阱

C 语言常见问题包括：

- 指针未初始化
- 数组越界
- 字符串缺少 `\0`
- `sizeof` 用错对象
- `malloc` 后忘记 `free`
- `free` 后继续使用指针
- 宏缺少括号
- 头文件重复包含
- 声明和定义混淆
- 有符号和无符号混用

这些问题在普通程序里可能只是崩溃，在设备控制里可能表现为误触发、通信异常、传感器读数错误、电机动作异常或系统死机。

所以 C 语言学习不能只追求语法会写，还要形成底层安全意识。

## 12. 嵌入式接口预览

C 语言学习最后会自然过渡到嵌入式接口：

- 通过指针访问寄存器地址。
- 通过位运算配置寄存器字段。
- 通过结构体组织设备状态。
- 通过函数封装驱动接口。
- 通过宏定义引脚、端口、命令和标志位。
- 通过 `volatile` 处理硬件寄存器和中断变量。
- 通过多文件工程组织驱动、业务和系统模块。

这正好连接到 STM32 课程。

# 三、STM32 部分

STM32 课程主要讲开发环境搭建和嵌入式项目的完整周期。

课程基于江协科技 STM32 入门教程，内容覆盖 50 集、15 章，总时长约 33 小时 30 分钟。它不是单纯讲概念，而是围绕真实硬件实验展开：LED、蜂鸣器、按键、光敏传感器、红外模块、旋转编码器、OLED、直流电机、舵机、MPU6050、W25Q64 等。

STM32 学习的主线是：

```text
认识芯片和开发环境
-> 建立工程
-> 控制 GPIO
-> 接入输入输出设备
-> 使用中断和定时器
-> 采集模拟量
-> 使用 DMA 提高效率
-> 用串口/I2C/SPI 通信
-> 管理时间、电源、看门狗和存储
```

## 第1章：课程与 STM32 概述

课程首先介绍硬件套件和 STM32 基本情况。

用到的硬件包括 STM32 最小系统板、面包板、杜邦线、OLED 显示屏、ST-Link、USB 转串口模块、Flash 存储器、蜂鸣器、光敏传感器、热敏传感器、红外模块、旋转编码器、LED、直流电机、电机驱动模块和舵机。

这些模块覆盖了设备控制里的几个基本类型：

- 输入：按键、光敏、热敏、红外、编码器、MPU6050。
- 输出：LED、蜂鸣器、OLED、舵机、电机。
- 通信：串口、I2C、SPI。
- 存储：外部 Flash、内部 Flash、备份寄存器。

STM32 的核心来自 ARM，芯片由 ST 意法半导体设计和生产。课程中使用的 STM32F103C8T6 是常见入门型号。

这一章还讲芯片引脚、最小系统板结构、BOOT 引脚、复位按键、晶振、电源指示灯、SWD 下载接口、稳压芯片和外围电路。

对设备控制来说，这一章建立一个重要认识：单片机不是一块抽象计算板，它由内核、总线、外设、引脚、电源和时钟共同组成。程序控制设备，本质上是配置这些硬件资源。

## 第2章：开发环境搭建

开发环境主要包括 Keil5 MDK、器件支持包、ST-Link 驱动和 USB 转串口驱动。

课程讲了新建 STM32 工程的过程。一个 STM32 工程不只是 `main.c`，还需要启动文件、芯片头文件、系统时钟配置文件、内核支持文件、外设库文件和用户代码。

启动文件是 `.s` 汇编文件，负责芯片上电后的最早期启动过程。它会设置中断向量表，最终跳到 `main` 函数。

`stm32f10x.h` 描述了 STM32 外设寄存器和地址。它让 C 程序可以用结构体和宏访问寄存器。

`system_stm32f10x.c/h` 负责系统时钟配置。

`core_cm3.c/h` 提供 Cortex-M3 内核相关定义和函数。

课程介绍了三种开发方式：

1. 寄存器开发：直接写寄存器，最贴近硬件。
2. 标准库开发：使用 ST 官方标准外设库函数，降低寄存器配置难度。
3. HAL 库开发：更高级、更跨系列的库，屏蔽更多芯片差异。

寄存器方式能帮助理解底层原理，库函数方式更适合实际快速开发。学习时最好先知道寄存器在做什么，再用库函数提高效率。

## 第3章：GPIO

GPIO 是通用输入输出口，是最基础的外设。

GPIO 输出可以控制 LED、蜂鸣器、继电器、电机驱动输入等。课程先讲 GPIO 的内部结构，包括输入驱动、输出驱动、保护二极管、推挽输出、开漏输出等。

LED 实验用于理解输出控制。程序配置 GPIO 为输出模式，然后通过设置输出寄存器控制引脚高低电平，从而让 LED 亮灭。

LED 闪烁和流水灯用于练习延时函数、循环控制和多个引脚组合控制。

蜂鸣器实验说明 GPIO 不只控制灯，也可以控制声音输出。

GPIO 输入用于读取外部状态，比如按键、光敏传感器。按键控制 LED、光敏传感器控制蜂鸣器，说明了设备控制里最基本的闭环：

```text
读取输入 -> 判断状态 -> 控制输出
```

这也是后面复杂控制系统的原型。

## 第4章：OLED 调试与显示

OLED 显示屏用于调试和显示状态。

在没有复杂调试工具时，OLED 可以直接显示变量、传感器数据、运行状态和错误信息。它让单片机程序从“看不见内部状态”变成“可以观察运行结果”。

课程先介绍 OLED 调试工具，再讲 OLED 显示屏的使用。实际项目中，OLED 常作为调试界面或小型设备的人机界面。

这一章的价值不只是会点亮屏幕，而是学会给嵌入式程序增加可观察性。

## 第5章：EXTI 外部中断

外部中断用于让单片机在外部事件发生时立即响应。

如果不用中断，程序只能一直轮询按键或传感器状态。轮询简单，但效率低，也可能错过短暂事件。

中断的思路是：外部信号变化时，硬件主动打断当前程序，跳到中断服务函数处理事件。

课程讲了 EXTI 外部中断，并用对射式红外传感器计次、旋转编码器计次做实验。

对射式红外模块可以检测遮挡次数，适合计数场景。旋转编码器可以检测旋转动作，适合旋钮输入或速度测量。

中断让设备能更及时地响应外部世界，是实时控制的基础。

## 第6章：TIM 定时器

定时器是 STM32 里非常核心的外设。这一章内容最多，覆盖定时中断、外部时钟、输出比较、PWM、输入捕获和编码器接口。

定时中断用于周期性执行任务。比如每 1ms 扫描按键，每 10ms 采集传感器，每 100ms 更新显示，每 1s 统计状态。

外部时钟模式可以让定时器根据外部脉冲计数。

输出比较可以在计数器到达某个值时改变输出状态。

PWM 是设备控制中极其常见的信号。它通过调节占空比控制平均输出功率。课程用 PWM 驱动 LED 呼吸灯、舵机和直流电机。

LED 呼吸灯说明 PWM 可以调亮度。

舵机控制说明 PWM 可以表示角度位置。

直流电机调速说明 PWM 可以控制电机速度。

输入捕获用于测量输入信号的频率、周期或脉宽。PWMI 模式可以测频率和占空比。

编码器接口用于读取编码器信号，进而实现测速。电机控制中，编码器反馈是速度闭环和位置闭环的重要来源。

这一章把设备控制推到核心区域：时间、频率、占空比、速度和反馈。

## 第7章：ADC 模数转换器

ADC 用于把模拟电压转换成数字量。

很多传感器输出的是模拟信号，比如光敏电阻、热敏电阻、电位器、某些压力或电流传感器。单片机不能直接理解连续电压，必须通过 ADC 采样成数字值。

课程讲 ADC 基本概念，以及单通道和多通道采集。

单通道适合读取一个模拟量。多通道适合同时读取多个传感器输入。

设备控制中，ADC 是“读取真实世界连续变化”的入口。温度、光照、电压、电流等信号，都常通过 ADC 进入程序。

## 第8章：DMA 直接存储器存取

DMA 可以在外设和内存之间自动搬运数据，减少 CPU 参与。

没有 DMA 时，CPU 需要不断读外设、写内存。如果数据量大或采样频率高，CPU 会被搬运数据占用。

DMA 的意义是让硬件帮忙搬数据。CPU 只需要配置源地址、目标地址、数据长度和触发条件。

课程讲 DMA 数据转运，以及 DMA 配合 ADC 多通道采样。

这对于设备控制很重要。比如连续采集传感器数据时，DMA 可以把 ADC 数据自动放进数组，CPU 只在需要处理时读取缓冲区。这样系统更高效，也更稳定。

## 第9章：USART 串口

USART 是最常用的串口通信外设。

串口可以让 STM32 和电脑、其他单片机、蓝牙模块、Wi-Fi 模块、调试工具通信。课程讲串口协议、串口外设、发送、接收、数据包和下载工具。

串口发送可以用于打印调试信息。比如输出传感器数据、当前状态、错误码。

串口接收可以用于接收电脑或上位机命令。比如设置参数、切换模式、控制电机。

课程还讲 HEX 数据包和文本数据包。HEX 包更适合机器解析，文本包更适合人调试。

串口数据包引入了通信协议意识：一条完整消息通常需要包头、长度、命令、数据和校验。否则接收端很难判断哪里是一条消息的开始和结束。

FlyMcu 和 STLINK Utility 用于下载和工具操作，帮助理解除了 Keil 之外的烧录方式。

## 第10章：I2C 通信

I2C 是常见的板级通信总线，适合连接传感器、EEPROM、RTC、OLED 等低速外设。

I2C 通常使用两根线：SCL 时钟线和 SDA 数据线。总线上可以挂多个设备，每个设备通过地址区分。

课程先讲 I2C 通信协议，再以 MPU6050 为例。MPU6050 是陀螺仪和加速度计，可以测量姿态相关数据，常用于平衡车、无人机、姿态检测和运动感知。

课程分别实现软件 I2C 和硬件 I2C 读写 MPU6050。

软件 I2C 是用 GPIO 模拟协议时序。它有助于理解协议细节。

硬件 I2C 是使用 STM32 自带 I2C 外设。它效率更高，更适合实际工程。

这一章让设备可以连接复杂传感器，是从简单输入输出走向真实感知系统的关键。

## 第11章：SPI 通信

SPI 也是常用通信总线，速度通常比 I2C 更快。

SPI 常用信号包括 SCK、MOSI、MISO 和片选线 CS。它适合连接 Flash、显示屏、ADC、无线模块等。

课程先讲 SPI 通信协议，再以 W25Q64 Flash 存储器为例。W25Q64 是外部 Flash，可以用于保存数据、参数、日志或资源。

课程分别实现软件 SPI 和硬件 SPI 读写 W25Q64。

软件 SPI 帮助理解时序，硬件 SPI 更适合工程使用。

和 I2C 相比，SPI 通常速度快、协议简单，但占用引脚更多。设备控制中要根据外设要求、速度要求和引脚资源选择通信方式。

## 第12章：BKP 与 RTC

这一章讲 Unix 时间戳、备份寄存器和 RTC 实时时钟。

Unix 时间戳是一种用秒数表示时间的方式，适合程序计算和存储。

RTC 可以让单片机记录真实时间。它常用 32.768kHz 晶振，即使主系统休眠，也可以继续计时。

BKP 备份寄存器可以在特定供电条件下保留少量数据。比如保存启动标志、校准值或关键状态。

设备控制中，时间非常重要。日志记录、定时任务、低功耗唤醒、数据采样时间戳，都需要 RTC 支持。

## 第13章：PWR 电源控制

PWR 电源控制用于管理功耗和运行模式。

课程讲修改主频、睡眠模式、停止模式和待机模式。

修改主频会影响性能和功耗。频率高，计算快，但耗电多；频率低，省电，但处理能力下降。

睡眠、停止、待机模式是不同层次的低功耗模式。设备在不需要一直工作时，可以进入低功耗状态，等待中断或 RTC 唤醒。

这对电池供电设备非常关键。比如传感器节点、便携设备、远程监测设备，不能一直高功耗运行。

## 第14章：WDG 看门狗

看门狗用于防止程序卡死后无人恢复。

程序需要定期“喂狗”。如果程序跑飞、死循环或阻塞，不能及时喂狗，看门狗就会复位系统。

课程讲独立看门狗和窗口看门狗。

独立看门狗使用独立时钟，可靠性更强，适合系统级保护。

窗口看门狗要求在规定时间窗口内喂狗，太早或太晚都不行，能发现更多异常时序问题。

设备控制系统常常要长期运行。看门狗是一种工程保险，保证系统异常时可以自动恢复。

## 第15章：FLASH 闪存

Flash 用于非易失存储。断电后数据仍然保留。

课程讲内部 Flash 的读写，以及读取芯片 ID。

内部 Flash 可以用于保存配置参数、校准数据、设备编号、运行次数等。外部 Flash 则适合保存更多数据，比如日志、波形、资源或历史记录。

Flash 操作需要注意擦除和写入粒度，也要注意寿命。Flash 不能像 RAM 一样无限次随便写，频繁写入要设计磨损均衡或减少写次数。

读取芯片 ID 可以用于设备身份识别、绑定、序列号或防止混淆。

# 四、C++ 部分

C++ 在设备控制方向上的作用，不是替代 C，也不是把所有嵌入式代码都写得很“高级”。它的价值是：在性能接近 C 的前提下，把复杂控制项目写得更安全、更可维护、更容易扩展。

个人总结里提到，C++ 主要用于编写更具可维护性和安全性的代码，实现算法和业务主程序，并完成部署。这句话可以拆成三层：

1. 更安全：减少裸指针、手动资源释放、宏滥用和重复代码带来的错误。
2. 更可维护：用类、接口、命名空间和模块化结构组织传感器、执行器、控制器和状态机。
3. 更适合算法和业务层：用模板、`constexpr`、`std::array` 等机制实现 PID、滤波器、轨迹规划、状态机和控制循环。

C++ 的核心原则是零开销抽象。也就是说，好的 C++ 写法应该让编译器在编译期完成尽可能多的工作，运行时开销接近手写 C。

## 1. 从 C 到 C++：不是换语言，而是升级组织方式

有 C 基础时，C++ 的很多底层知识是连续的。数组、指针、位运算、结构体、编译链接、内存布局，这些仍然重要。

C++ 新增的关键能力在于：

- 引用：比指针更安全的参数传递方式。
- 函数重载：同一语义可以使用同一个函数名。
- 命名空间：避免不同模块命名冲突。
- 类和对象：把数据和操作封装在一起。
- 构造和析构：对象创建和销毁时自动初始化、清理。
- RAII：用对象生命周期管理硬件资源。
- 继承和多态：为传感器、执行器等设备建立统一接口。
- 模板：让控制算法对不同数据类型复用。
- Modern C++ 特性：用 `constexpr`、`enum class`、`static_assert` 等增强安全性。

在设备控制里，C++ 常常不直接用于最底层寄存器位操作，而是用于驱动封装、控制算法、业务主程序和部署框架。底层仍然可以调用 C 或 HAL API，上层用 C++ 把系统组织起来。

## 2. 引用、函数重载和命名空间

引用可以理解为变量的别名。它声明时必须绑定对象，之后不能改绑，也不能像指针一样为 `nullptr`。

这让引用很适合函数参数：

```cpp
void updateConfig(const Config& cfg);
```

这里 `const Config&` 避免了大对象拷贝，也承诺函数不会修改配置。相比指针，调用者不需要担心空指针。

指针仍然有用途。可选参数、数组缓冲区、底层硬件地址和可能为空的对象，仍然适合用指针表达。

函数重载允许多个函数使用同一个名字，只要参数不同即可：

```cpp
void write(uint8_t data);
void write(const uint8_t* buf, size_t len);
```

在 C 里可能要写成 `write_byte` 和 `write_buf`。C++ 里可以用同一个 `write`，编译器根据参数选择版本。这让接口更接近人的语义。

命名空间用于组织模块：

```cpp
namespace motor { void init(); }
namespace sensor { void init(); }
```

设备项目里，经常会有电机、传感器、通信、显示、控制算法等模块。命名空间可以减少命名冲突，让代码结构更清楚。

## 3. 类和对象：把设备封装成可操作的模块

C 语言里常见写法是结构体加函数：

```c
struct Motor {
    int pwm_pin;
    int dir_pin;
};

void motor_set_speed(struct Motor* m, int speed);
```

C++ 把这种模式变成语言级封装：

```cpp
class Motor {
    int pwm_pin;
    int dir_pin;
public:
    Motor(int pwm, int dir) : pwm_pin(pwm), dir_pin(dir) {}
    void setSpeed(int speed);
};
```

这样，数据和操作它的函数放在同一个类型里。调用也更自然：

```cpp
motor.setSpeed(100);
```

对设备控制来说，类很适合表达“一个真实设备”：

- `Motor` 表示电机。
- `Encoder` 表示编码器。
- `AdcReader` 表示 ADC 采样通道。
- `UartPort` 表示串口。
- `PidController` 表示 PID 控制器。
- `ControlLoop` 表示主控制循环。

封装的价值在于限制错误。比如电机的方向脚、PWM 脚、当前限幅和输出函数都封装在 `Motor` 里，上层业务不需要知道底层细节，只调用 `setSpeed()`。

## 4. 构造、析构和 RAII：自动管理资源生命周期

C++ 对嵌入式很有价值的一点是 RAII。

RAII 的意思是：构造时获取资源，析构时释放资源。

在普通软件里，资源可能是内存、文件、锁。在嵌入式里，资源可以是 GPIO 模式、SPI 片选、DMA 缓冲区、串口事务、定时器通道、电机输出状态。

比如 SPI 事务可以这样写：

```cpp
class SpiTransaction {
    int cs_pin;
public:
    explicit SpiTransaction(int cs) : cs_pin(cs) {
        spi_begin();
        digitalWrite(cs_pin, LOW);
    }

    ~SpiTransaction() {
        digitalWrite(cs_pin, HIGH);
        spi_end();
    }
};
```

使用时：

```cpp
void readSensor() {
    SpiTransaction transaction(CS_PIN);
    auto data = spi_transfer(0x00);
}
```

函数结束时，`transaction` 自动析构，片选自动拉高，SPI 自动释放。这样就不容易因为某个 `return` 分支忘记释放资源。

在设备控制中，RAII 可以减少很多隐蔽错误：

- SPI 片选拉低后忘记拉高。
- 电机启动后异常返回，没有停机。
- DMA 缓冲区申请后没有归还。
- GPIO 临时改成输出后没有恢复。
- 中断临界区进入后没有退出。

C 里这些全靠纪律。C++ 可以让编译器帮你保证“离开作用域就清理”。

## 5. 拷贝控制和移动语义：避免资源被错误复制

C++ 对象默认可以拷贝。默认拷贝是逐成员拷贝，也叫浅拷贝。

如果对象只是普通数值，比如一个二维向量，浅拷贝没问题。但如果对象管理硬件资源或动态内存，默认拷贝就危险。

比如一个 `Motor` 对象表示真实电机。如果随便拷贝出两个 `Motor` 对象，它们可能都认为自己拥有同一个 PWM 通道。这样控制逻辑会混乱。

嵌入式里很多设备对象应该禁止拷贝：

```cpp
class Motor {
public:
    Motor(const Motor&) = delete;
    Motor& operator=(const Motor&) = delete;
};
```

移动语义用于转移资源所有权。比如一个缓冲区对象可以把内部指针“交给”另一个对象，自己变为空。移动语义能减少临时对象拷贝，但在嵌入式中要谨慎使用，保持所有权清楚。

## 6. 继承和多态：统一传感器与执行器接口

设备控制项目常常有多个传感器，读取方式不同，但上层只关心“读数”。

比如温度传感器可能走 I2C，压力传感器可能走 SPI，编码器可能走定时器，ADC 传感器可能走模拟采样。底层不同，上层希望统一处理。

C++ 可以用接口类表达：

```cpp
class Sensor {
public:
    virtual float read() = 0;
    virtual ~Sensor() = default;
};
```

不同传感器继承它：

```cpp
class TemperatureSensor : public Sensor {
public:
    float read() override;
};

class EncoderSensor : public Sensor {
public:
    float read() override;
};
```

上层控制器只依赖 `Sensor` 接口，不关心具体实现。这让设备替换更容易。

多态的代价是虚函数表和一次间接调用。对很多设备控制业务层来说，这个代价可以接受。但在高频中断、极端性能路径里，要谨慎使用虚函数。

基类析构函数如果用于多态，必须是虚析构。否则通过基类指针删除派生类对象时，派生类析构可能不会执行。

## 7. 模板：让控制算法泛型化

模板是 C++ 在嵌入式控制算法中非常有价值的能力。

一个 PID 控制器可能要支持 `float`、`double`、整数、定点数。C 语言里常常需要写多份代码，或者用宏绕过去。C++ 模板可以写一份：

```cpp
template<typename T>
class Pid {
    T kp;
    T ki;
    T kd;
    T integral{};
    T last_error{};
public:
    Pid(T p, T i, T d) : kp(p), ki(i), kd(d) {}

    T compute(T target, T current) {
        T error = target - current;
        integral += error;
        T derivative = error - last_error;
        last_error = error;
        return kp * error + ki * integral + kd * derivative;
    }
};
```

使用时：

```cpp
Pid<float> speed_pid(1.0f, 0.1f, 0.01f);
Pid<int> position_pid(10, 2, 1);
```

模板在编译期展开。也就是说，编译器会根据具体类型生成对应代码，运行时没有额外类型分发开销。

除了 PID，模板还适合：

- 低通滤波器
- 限幅器
- 斜坡限制器
- 环形缓冲区
- 定长矩阵
- 均值滤波
- 状态机事件处理
- 运动控制器

要注意模板膨胀。如果同一个模板用太多类型实例化，最终固件体积可能变大。嵌入式里要控制模板实例数量。

## 8. Modern C++：适合嵌入式的安全特性

Modern C++ 里有一些特性特别适合设备控制。

`nullptr` 替代 `NULL`，类型更安全。

`auto` 可以减少冗长类型，但不应该滥用到看不出变量含义。

`constexpr` 可以把常量和简单计算放到编译期：

```cpp
namespace Config {
    constexpr float CONTROL_FREQ = 100.0f;
    constexpr float DT = 1.0f / CONTROL_FREQ;
    constexpr uint32_t BAUD_RATE = 115200;
}
```

这类配置不会增加运行时计算开销。

`enum class` 比 C 风格枚举更安全：

```cpp
enum class MotorMode {
    Stop,
    SpeedControl,
    PositionControl
};
```

它不会随便隐式转成整数，也不容易和其他枚举名冲突。

`static_assert` 可以在编译期检查配置：

```cpp
static_assert(NUM_SENSORS <= 8, "Too many sensors");
```

设备项目里，很多错误越早暴露越好。能在编译期报错，就不要等运行时才发现。

`override` 可以让编译器检查派生类是否真的覆盖了虚函数，避免函数签名写错。

`std::array<T, N>` 很适合替代 C 数组。它大小固定，不需要堆内存，还能自带长度信息。

## 9. STL 和智能指针的嵌入式取舍

C++ 标准库不是不能用于嵌入式，而是要有选择地用。

推荐使用：

- `std::array`：固定大小数组，适合采样缓存、通道列表、滤波窗口。
- `std::span`：如果工具链支持，可用来安全传递数组视图。
- `std::optional`：表达可能没有结果，比魔法错误码更清晰。
- `std::unique_ptr`：独占所有权，开销接近裸指针。

谨慎使用：

- `std::vector`：会使用堆内存，适合内存较大的平台，不适合小单片机随意使用。
- `std::map`、`std::set`：通常动态分配多，代码体积也可能偏大。
- `std::shared_ptr`：有引用计数，开销更高，资源受限设备上要谨慎。

通常不建议在小型嵌入式项目中开启：

- 异常：需要额外代码和栈展开机制。
- RTTI：运行时类型识别会增加体积。

很多嵌入式 C++ 项目会使用类似策略：

```text
关闭异常
关闭 RTTI
少用 new/delete
优先栈分配和静态分配
优先 std::array
谨慎使用 vector
高频路径避免虚函数
```

## 10. C++ 设备控制架构

一个嵌入式 C++ 控制项目可以分层：

```text
应用层：ControlLoop, StateMachine, SafetyManager
    ↓
算法层：Pid, LowPassFilter, MotionPlanner, Limiters
    ↓
设备层：Motor, Encoder, Sensor, Display, Actuator
    ↓
驱动层：GpioPin, SpiBus, I2cBus, TimerChannel, AdcReader
    ↓
硬件层：寄存器 / HAL / 标准库 / BSP
```

底层驱动层靠近硬件，要求简单、确定、可靠。

设备层把硬件模块封装成对象，比如电机、编码器、显示屏。

算法层实现可复用控制算法，比如 PID、滤波、轨迹规划和限幅。

应用层组合多个设备和算法，形成具体业务逻辑，比如电机定速、定位控制、倒立摆、自动启停、故障保护。

这种分层比所有代码都堆在 `main` 里更容易维护，也方便测试和替换模块。

## 11. C++ 和算法题训练

personal 文件里提到题库：LeetCode 热题 100、剑指 Offer 50 题。

这些题不直接等于嵌入式控制项目，但能训练 C++ 的算法和数据结构能力：

- 数组和双指针：适合理解缓冲区、采样窗口、滑动统计。
- 链表：帮助理解指针、所有权和动态结构。
- 栈和队列：适合状态机、事件队列、任务调度。
- 哈希表：适合查找和映射，但嵌入式中要注意内存。
- 二叉树和递归：训练结构化思维，小单片机中递归要谨慎。
- 动态规划：训练状态定义和状态转移，和控制系统中的状态思维有相通之处。
- 堆和优先队列：适合任务优先级、事件调度等场景。

刷题的价值不是为了在设备代码里大量使用复杂容器，而是为了提升用 C++ 写清楚算法、边界条件和数据结构的能力。

在设备控制方向，算法题训练要和工程约束结合起来：

- 写代码时关注边界条件。
- 避免不受控的动态内存。
- 清楚时间复杂度和空间复杂度。
- 能把算法封装成可测试的小模块。
- 能把模块接入主控制循环。

## 12. C++ 部署到设备端的注意点

C++ 部署到设备端时，要关注工具链和运行时特性。

首先确认编译器支持的 C++ 标准，比如 C++11、C++14、C++17。嵌入式常用特性不一定需要最新标准，C++11 已经能覆盖引用、类、RAII、模板、`constexpr`、`enum class`、`override`、`nullptr` 等核心能力。

其次要确认启动代码和链接脚本是否支持 C++ 全局对象构造。全局对象会在 `main` 前构造，顺序和依赖要小心。嵌入式中更推荐明确初始化，而不是依赖复杂全局对象。

再次要控制运行时特性。很多项目会关闭异常和 RTTI，减少固件体积和不确定性。

最后要关注内存。C++ 不是问题，失控的堆分配才是问题。只要遵守栈分配、静态分配、固定容量容器、明确所有权这些原则，C++ 可以很好地用于嵌入式自动控制。

# 五、PyTorch 部分

PyTorch 在设备控制方向上的作用，主要不是直接跑在小型 STM32 单片机上，而是在设备外完成机器学习模型的实现、训练、验证和导出。训练好的模型可以再通过合适的部署链路接入设备控制系统。

personal 文件里写到：需要 PyTorch 实现一些机器学习算法。把这句话放到设备控制里，可以理解为：当传统规则、PID 或手写阈值难以处理复杂数据时，用 PyTorch 从数据里学习模型。

典型场景包括：

- 用图像模型做工业缺陷检测、目标识别、姿态识别。
- 用时序模型分析振动、电流、温度等传感器数据。
- 用分类模型判断设备状态，比如正常、轻微异常、严重异常。
- 用回归模型预测负载、寿命、能耗或未来状态。
- 用强化学习或模仿学习探索控制策略。
- 用神经网络作为 MPC、状态估计或故障预测中的模型组件。

PyTorch 的意义是把机器学习算法从“公式”变成“可训练、可验证、可保存、可部署的工程流程”。

## 1. Tensor：PyTorch 的基础数据结构

Tensor 是 PyTorch 的基础单位，可以理解成支持 GPU 和自动求导的多维数组。

它和 NumPy 的 `ndarray` 很像，都支持多维数据、切片、广播、矩阵乘法和形状变换。但 Tensor 多了两个关键能力：

1. 可以放到 CPU、GPU 或 Apple M 系列芯片的 MPS 设备上计算。
2. 可以追踪计算过程，并自动计算梯度。

常见创建方式包括：

```python
torch.tensor([1, 2, 3])
torch.zeros(3, 4)
torch.ones(3, 4)
torch.randn(3, 4)
torch.arange(10)
torch.eye(3)
```

设备控制里的数据也可以自然表示成 Tensor：

- 一批传感器数据：`[batch, channels]`
- 一段时间序列：`[batch, time, features]`
- 一张图像：`[batch, channels, height, width]`
- 一批控制状态：`[batch, state_dim]`

理解 Tensor，就是理解 PyTorch 里数据如何流动。

## 2. Autograd：自动求导和计算图

训练神经网络的关键是反向传播。也就是根据损失函数，计算每个参数应该往哪个方向调整。

如果手写反向传播，网络稍微复杂一点就会非常困难。PyTorch 的 Autograd 会自动追踪 Tensor 的计算过程，并在调用 `backward()` 时按链式法则反向求导。

当一个 Tensor 设置了：

```python
requires_grad=True
```

PyTorch 就会记录它参与的运算。

比如：

```python
x = torch.tensor([2.0], requires_grad=True)
w = torch.tensor([3.0], requires_grad=True)
y = w * x + 1
y.backward()
```

这里 `y` 的计算过程会形成一张动态计算图。`backward()` 会沿着图反向走，把梯度写入 `x.grad` 和 `w.grad`。

PyTorch 的计算图是动态图，也叫 define-by-run。意思是：你写的 Python 代码每运行一次，就真实构建一次计算图。这让调试很直观，可以在 `forward()` 里打印形状、查看中间变量，也能写比较灵活的模型结构。

设备控制里，如果要训练一个从传感器数据预测设备状态的模型，Autograd 负责自动计算模型参数对预测误差的梯度。开发者只需要写前向计算和损失函数。

## 3. nn.Module：搭建神经网络的标准方式

PyTorch 中的模型通常继承 `nn.Module`。

基本写法是：

```python
class MyNet(nn.Module):
    def __init__(self):
        super().__init__()
        self.fc = nn.Linear(10, 2)

    def forward(self, x):
        return self.fc(x)
```

`nn.Module` 主要帮你做三件事：

1. 参数注册：把模型里的可训练参数收集起来，供优化器更新。
2. 子模块管理：模型里嵌套的层会被递归管理。
3. 设备迁移：`model.to(device)` 可以把所有参数搬到目标设备。

常用层包括：

- `nn.Linear`：全连接层，适合表格特征、状态向量、传感器统计特征。
- `nn.Conv1d`：一维卷积，适合时间序列、振动信号、电流波形。
- `nn.Conv2d`：二维卷积，适合图像。
- `nn.LSTM`、`nn.GRU`：循环网络，适合序列。
- `nn.Transformer`：适合复杂序列建模。
- `nn.BatchNorm`、`nn.Dropout`、`nn.ReLU`：训练稳定性和非线性表达。

一个设备状态分类模型可能输入传感器特征，输出状态类别；一个故障预测模型可能输入历史窗口，输出未来风险分数；一个视觉检测模型可能输入图像，输出缺陷类别。

## 4. 损失函数和优化器

损失函数用于衡量模型预测和真实答案之间的差距。

常见选择是：

- 回归任务：`nn.MSELoss`
- 多分类任务：`nn.CrossEntropyLoss`
- 二分类任务：`nn.BCEWithLogitsLoss`

在设备控制中：

- 预测温度、能耗、剩余寿命，是回归任务。
- 判断设备属于哪种故障类型，是多分类任务。
- 判断是否异常，是二分类任务。

优化器负责根据梯度更新参数。常见优化器有：

- `SGD`
- `SGD + Momentum`
- `Adam`
- `AdamW`
- `RMSprop`

典型训练步骤是：

```python
optimizer.zero_grad()
pred = model(x)
loss = loss_fn(pred, y)
loss.backward()
optimizer.step()
```

`zero_grad()` 很重要，因为 PyTorch 默认会累积梯度。如果每个 batch 不清空梯度，就会把前几轮的梯度叠在一起，除非你是故意做梯度累积。

## 5. Dataset 和 DataLoader：把数据送进模型

训练模型不能只写网络，还要把数据稳定送进去。

PyTorch 用 `Dataset` 表示数据集，用 `DataLoader` 负责分 batch、打乱、多进程加载和组装 batch。

自定义数据集通常实现两个方法：

```python
class MyDataset(Dataset):
    def __len__(self):
        return len(self.data)

    def __getitem__(self, idx):
        return self.data[idx], self.labels[idx]
```

然后用 DataLoader：

```python
loader = DataLoader(dataset, batch_size=32, shuffle=True, num_workers=4)
```

设备控制数据常常来自：

- 传感器日志
- 电机运行曲线
- 串口采样文件
- 工业相机图像
- 故障记录
- 标注后的状态样本

数据管线要特别注意时间顺序和数据泄漏。比如时序预测任务不能把未来数据混进训练特征里；故障检测任务要避免同一设备的相邻片段同时出现在训练集和测试集，导致评估虚高。

## 6. 训练循环和验证循环

一个完整训练循环通常包括训练和验证两部分。

训练时：

```python
model.train()
for x, y in train_loader:
    x, y = x.to(device), y.to(device)
    pred = model(x)
    loss = loss_fn(pred, y)
    optimizer.zero_grad()
    loss.backward()
    optimizer.step()
```

验证时：

```python
model.eval()
with torch.no_grad():
    for x, y in val_loader:
        x, y = x.to(device), y.to(device)
        pred = model(x)
        loss = loss_fn(pred, y)
```

`model.train()` 和 `model.eval()` 会影响 Dropout 和 BatchNorm 的行为。

`torch.no_grad()` 会关闭梯度追踪，减少显存占用并加快验证。

这两个概念不能混淆。`eval()` 不会自动关闭梯度，`no_grad()` 也不会自动切换 Dropout 和 BatchNorm 模式。验证时通常两个都要用。

对于设备控制模型，验证集非常重要。模型不能只在采集过的数据上表现好，还要能泛化到新的设备、新的工况、新的噪声和新的环境。

## 7. Device Management：CPU、GPU 和 MPS

PyTorch 支持把模型和数据放到不同设备上计算。

常见写法：

```python
device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)
```

Mac 上可以使用 MPS：

```python
device = torch.device("mps" if torch.backends.mps.is_available() else "cpu")
```

训练时，模型和输入数据必须在同一个设备上。如果模型在 GPU，输入还在 CPU，运算会报错。

设备控制中的机器学习模型，训练阶段可以在 GPU 上完成。部署阶段则要根据目标平台选择不同方式：

- 上位机或边缘计算盒：可以直接用 PyTorch 或 TorchScript。
- NVIDIA Jetson：可以考虑 PyTorch、TensorRT、ONNX。
- 移动端或嵌入式 Linux：可以考虑 ONNX Runtime、TensorRT、OpenVINO 等。
- 小型 MCU：通常需要转成更轻量的推理框架，比如 TFLite Micro、CMSIS-NN 或厂商工具链，PyTorch 本身不是直接运行环境。

## 8. 保存、加载和 checkpoint

训练好的模型需要保存。

推荐保存 `state_dict`，而不是直接保存整个模型对象：

```python
torch.save(model.state_dict(), "model.pth")
```

加载时：

```python
model = MyNet()
model.load_state_dict(torch.load("model.pth"))
model.eval()
```

如果要恢复训练，需要同时保存优化器状态和 epoch：

```python
torch.save({
    "epoch": epoch,
    "model_state_dict": model.state_dict(),
    "optimizer_state_dict": optimizer.state_dict(),
    "loss": loss,
}, "checkpoint.pth")
```

设备控制项目里，保存模型不只是为了以后继续训练，也用于模型版本管理。比如不同工况、不同设备型号、不同传感器版本，可能需要不同模型。必须记录训练数据版本、模型结构、指标和导出文件。

## 9. 混合精度、梯度累积和训练加速

训练深度模型时，显存和速度经常是瓶颈。

混合精度训练 AMP 使用 FP16 或 BF16 进行部分计算，同时保留必要的 FP32 精度。它可以减少显存占用、提高训练速度。

典型写法是：

```python
scaler = torch.cuda.amp.GradScaler()

with torch.cuda.amp.autocast():
    pred = model(x)
    loss = loss_fn(pred, y)

scaler.scale(loss).backward()
scaler.step(optimizer)
scaler.update()
```

梯度累积用于显存不够但想模拟大 batch 的情况。做法是多个小 batch 都 `backward()`，累计到一定步数后再 `optimizer.step()`。

PyTorch 2.0 之后还提供了 `torch.compile`，可以对模型进行编译优化：

```python
model = torch.compile(model)
```

它会尝试进行算子融合和内存优化，某些模型可以明显加速。

对于设备控制项目，这些能力主要用于训练阶段。训练越高效，模型迭代越快，越容易比较不同特征、不同网络结构和不同数据处理方案。

## 10. 模型导出和部署链路

PyTorch 训练出来的模型，最终要进入设备控制系统，需要考虑部署格式。

常见路径包括：

- 保存 `state_dict`：适合继续在 PyTorch 环境中加载。
- TorchScript：把模型转成可序列化、可脱离 Python 部分运行的形式。
- ONNX：跨框架交换格式，方便接入 ONNX Runtime、TensorRT、OpenVINO 等推理后端。
- TensorRT：适合 NVIDIA GPU/Jetson 平台高性能推理。
- 量化：把 FP32 模型转成 INT8 或其他低精度，降低算力和内存需求。

设备控制里部署模型时，要关注：

- 推理延迟：是否满足控制周期。
- 模型大小：是否能放进目标设备。
- 内存占用：运行时是否稳定。
- 输入预处理：训练和部署必须一致。
- 输出后处理：分类阈值、异常分数、控制决策逻辑必须清楚。
- 失败保护：模型输出异常时，系统要能回退到安全策略。

机器学习模型不能直接无保护地控制执行器。更稳妥的方式是：模型提供感知、预测或辅助决策，底层控制和安全限幅仍由确定性逻辑保护。

## 11. PyTorch 在设备控制中的典型工作流

一个把 PyTorch 接入设备控制的项目，可以按这个流程走：

```text
明确任务
-> 采集设备数据
-> 清洗数据和标注
-> 划分训练/验证/测试集
-> 构建 Dataset 和 DataLoader
-> 定义模型 nn.Module
-> 选择损失函数和优化器
-> 训练和验证
-> 做错误分析
-> 保存 checkpoint 和最终模型
-> 导出模型
-> 在目标平台验证推理
-> 接入控制系统
-> 加入安全保护和监控
```

比如做电机故障检测：

1. 采集电流、振动、转速等数据。
2. 按正常、轴承异常、负载异常等类别标注。
3. 用 1D CNN 或 LSTM 训练分类模型。
4. 验证模型在未见过设备或工况上的表现。
5. 导出模型到边缘设备。
6. 控制系统读取模型输出，触发报警、降速或停机保护。

再比如做视觉质检：

1. 采集工业相机图像。
2. 标注正常、划痕、裂纹、缺口等类别。
3. 用 CNN 或检测模型训练。
4. 部署到边缘计算设备。
5. 将检测结果反馈给 PLC、机械臂或分拣机构。

## 12. 常见误区

PyTorch 学习和使用中常见误区包括：

- 在 `__init__` 里直接赋值普通 Tensor，导致参数没有被注册。应该使用 `nn.Parameter` 或 `nn.Module`。
- 验证时只写 `model.eval()`，忘了 `torch.no_grad()`，导致显存浪费。
- 以为 `torch.no_grad()` 会关闭 Dropout，实际上还需要 `model.eval()`。
- 忘记 `optimizer.zero_grad()`，导致梯度意外累积。
- CPU Tensor 和 GPU Tensor 混合运算。
- 分类任务使用 `CrossEntropyLoss` 时，模型最后又手动加了 softmax。
- 保存整个模型对象，导致后续加载和代码兼容困难。推荐保存 `state_dict`。
- 用测试集反复调参，导致最终指标失真。
- 训练指标很好，但没有检查部署端预处理是否一致。
- 模型输出直接控制执行器，没有安全限幅和异常回退。

这些误区本质上都和工程可靠性有关。设备控制系统比普通离线模型更强调稳定性，因为模型结果可能影响真实硬件动作。

# 六、完整嵌入式项目周期

个人总结里提到 STM32 项目的完整周期，这一点很重要。

一个设备控制项目通常不是直接写 `main`，而是从硬件理解开始：

```text
阅读设备手册
-> 确认电气特性和通信方式
-> 搭建最小测试电路
-> 编写单个驱动
-> 验证驱动功能
-> 组合多个传感器和执行器
-> 写主程序业务逻辑
-> 调试、优化、异常保护
-> 固化为完整设备程序
```

阅读设备手册是第一步。因为传感器和执行器不是抽象模块，它们有供电电压、引脚定义、通信时序、寄存器地址、数据格式、最大电流、采样频率和初始化流程。

驱动代码负责把硬件细节封装起来。比如 `MPU6050_ReadData()` 隐藏 I2C 读寄存器细节，`OLED_ShowString()` 隐藏显示屏通信细节，`Motor_SetSpeed()` 隐藏 PWM 配置细节。

主函数负责组合驱动，形成业务流程。比如：

```text
初始化时钟
初始化 GPIO
初始化 OLED
初始化串口
初始化传感器
初始化定时器和中断
while(1) {
    读取传感器
    处理数据
    控制执行器
    更新显示
    通过串口发送状态
}
```

随着项目变复杂，主循环里不能什么都塞。需要按模块拆分代码，用定时器、中断、缓冲区、状态机和通信协议来组织系统。

# 七、C、C++、STM32 和 PyTorch 的对应关系

C、C++、STM32 和 PyTorch 不是四套割裂的东西。C 更贴近底层寄存器和驱动，STM32 提供真实硬件平台，C++ 负责把驱动、算法和业务逻辑组织成更可维护的工程结构，PyTorch 负责把机器学习模型训练出来，并为智能感知、预测和辅助决策提供模型来源。

| 能力 | 设备控制中的用途 |
|---|---|
| C 编译与链接 | 建工程、加启动文件、加库文件、配置头文件路径 |
| C 类型系统 | 定义寄存器值、传感器数据、通信字段 |
| C 指针 | 访问寄存器、传递缓冲区、修改外部变量 |
| C 数组 | 保存采样数据、串口缓冲区、显示缓存 |
| C 结构体 | 封装外设配置、传感器数据、通信包 |
| C 函数指针 | 回调、中断事件、状态机、命令分发 |
| C 位运算 | 设置/清除寄存器位、处理标志位 |
| C `volatile` | 硬件寄存器、中断变量、防止错误优化 |
| STM32 GPIO/ADC/TIM | 连接真实输入、输出、采样和定时任务 |
| STM32 USART/I2C/SPI | 连接上位机、传感器、Flash 和外设模块 |
| STM32 DMA/中断 | 提高实时性，减少 CPU 搬运数据的负担 |
| C++ 类和封装 | 把电机、传感器、串口、显示屏封装成对象 |
| C++ RAII | 自动管理 SPI 片选、GPIO 模式、DMA 缓冲区等资源 |
| C++ 模板 | 泛型化 PID、滤波器、限幅器、环形缓冲区 |
| C++ 多态 | 统一传感器、执行器、显示设备的上层接口 |
| C++ `constexpr`/`enum class` | 编译期配置和类型安全状态定义 |
| C++ `std::array` | 固定容量缓存，替代裸数组并保留大小信息 |
| PyTorch Tensor | 表示传感器批数据、图像、时序窗口和状态向量 |
| PyTorch Autograd | 自动计算模型梯度，训练机器学习算法 |
| PyTorch `nn.Module` | 搭建故障检测、状态分类、视觉识别、时序预测模型 |
| Dataset/DataLoader | 管理设备日志、图像、传感器数据的训练输入 |
| 训练/验证循环 | 评估模型是否能泛化到新设备和新工况 |
| state_dict/checkpoint | 保存模型参数、恢复训练、管理模型版本 |
| ONNX/TorchScript/量化 | 为边缘设备或部署端准备推理模型 |

这张表说明：学习 C 是为了读懂并写出设备驱动；学习 STM32 是为了把驱动连到真实硬件；学习 C++ 是为了把越来越复杂的算法和业务逻辑组织成可长期维护的系统；学习 PyTorch 是为了从数据中训练模型，让设备控制系统具备识别、预测和辅助决策能力。

# 八、放在设备控制中的最终理解

设备控制程序的核心闭环是：

```text
感知输入 -> 计算判断 -> 控制输出 -> 反馈修正
```

GPIO 输入、ADC、I2C、SPI、USART 负责感知和通信。

定时器、中断、DMA 负责让系统按正确时间和效率运行。

GPIO 输出、PWM、舵机、电机驱动负责控制动作。

OLED、串口、Flash、RTC 负责显示、调试、记录和保存状态。

看门狗和电源控制负责可靠性和低功耗。

C 语言贯穿底层环节。它把外设封装成驱动函数，再由主程序组合成完整业务。

C++ 则适合把这些驱动函数进一步组织成对象和模块。比如用 `Motor` 封装 PWM 和方向控制，用 `Encoder` 封装计数和速度计算，用 `Pid<float>` 封装控制算法，用 `ControlLoop` 组合传感器、控制器和执行器。

PyTorch 则适合在设备外训练模型。比如用振动数据训练故障检测模型，用工业图像训练缺陷识别模型，用电流和转速序列训练状态预测模型。训练好的模型再经过导出、压缩或转换，接入边缘设备、上位机或嵌入式 Linux 平台。

这样，设备控制程序可以从“很多函数堆在一起”，升级成“底层驱动清楚、设备对象清楚、算法模块清楚、业务流程清楚、机器学习模型来源清楚”的工程。

# 十、最后总结

这部分课程的主线很清楚：先用 C 语言建立底层编程能力，再用 STM32 把这些能力落到真实硬件控制上，然后用 C++ 把算法和业务主程序组织成更安全、更可维护的工程，最后用 PyTorch 实现和训练机器学习模型，让设备控制系统具备从数据中学习的能力。

C 语言部分解决“程序如何贴近内存和硬件”。重点是指针、数组、结构体、位运算、宏、编译链接和 `volatile`。这些内容都是写嵌入式驱动必须掌握的基础。

STM32 部分解决“程序如何控制真实设备”。从 GPIO 到定时器，从 ADC 到 DMA，从串口到 I2C/SPI，再到 RTC、电源、看门狗和 Flash，覆盖了一个单片机项目最常见的外设能力。

C++ 部分解决“程序如何长期维护和扩展”。重点是类、RAII、模板、多态、`constexpr`、`enum class`、`std::array` 和嵌入式 STL 取舍。它适合实现 PID、滤波器、限幅器、状态机、设备抽象层和业务控制循环。

PyTorch 部分解决“机器学习算法如何实现和训练”。重点是 Tensor、Autograd、`nn.Module`、Dataset/DataLoader、训练循环、验证循环、GPU 加速、模型保存加载、导出和部署前验证。它适合训练故障检测、视觉识别、状态分类、时序预测等模型。

放在设备控制方向看，最终目标不是孤立地会写 C 或会点亮 LED，而是能完成完整流程：

1. 看懂硬件手册。
2. 搭建工程和开发环境。
3. 编写并验证单个外设驱动。
4. 组合多个传感器和执行器。
5. 用 C++ 或清晰模块化方式封装设备对象和控制算法。
6. 在主程序中实现业务控制逻辑和状态机。
7. 用 PyTorch 训练需要的机器学习模型。
8. 导出、压缩或转换模型，并在目标平台验证推理结果。
9. 加入通信、显示、存储、低功耗和异常保护。
10. 控制内存、异常、RTTI、堆分配、模型大小和推理延迟，完成设备端部署。

也就是说，这门“编程”总结对应的是设备控制的底座能力：用 C 贴近硬件，用 STM32 控制真实设备，用 C++ 组织复杂算法和业务流程，用 PyTorch 训练智能模型，最终把可靠的控制程序和经过验证的模型能力部署到设备控制系统中。
